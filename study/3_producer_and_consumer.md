#### Producer & Consumer

---
**Producer**

`Producer` — это компонент, который создаёт и отправляет сообщения в определённый топик Kafka.
Его основная задача — доставить данные в брокер `Kafka` (сервер, хранящий сообщения) так, чтобы они были:

- записаны корректно,

- не потерялись при сбое,

- и при этом не замедляли систему.

⚙️ Как происходит отправка

1. Приложение (например, сервис заказов) формирует сообщение — JSON, строку, событие и т.д.

2. Producer сериализует данные и отправляет их в Kafka.

3. Kafka принимает сообщение и сохраняет его в нужную партицию топика.

4. Producer получает подтверждение (ack) о том, что запись успешна.

Главные параметры определяют баланс надёжности и скорости.


🔹 **Идемпотентность**

Включается: `enable.idempotence=true`.

Гарантирует, что при повторной отправке сообщение не продублируется. `Kafka` делает это за счёт уникальных `sequence numbers`. Если сеть упала и продюсер повторил запись, то без идемпотентности появятся дубликаты, а с ней `Kafka` их отклонит. Это обязательная настройка для критичных систем вроде биллинга.

```java
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("enable.idempotence", "true"); // гарантии exactly-once
KafkaProducer<String, String> producer = new KafkaProducer<>(props);
```
🔹 **acks — подтверждения доставки**

Другой ключевой параметр — `acks`. Он определяет, кого ждёт продюсер после отправки:

| Значение    | Что означает                   | Плюсы                    | Минусы                                | 
|-------------|--------------------------------|--------------------------|---------------------------------------|
| `acks=0`    | Продюсер не ждёт подтверждений | Максимальная скорость    | Возможна потеря сообщений             | 
| `acks=1`    | Ждём лидера партиции           | Быстрее, меньше задержка | Если лидер упадёт — данные потеряются |
| `acks=all`  | Ждём все реплики               | Максимальная надёжность  | Меньшая производительность            |


```java
props.put("acks", "all");
```

🔹 **linger.ms и batch.size**

Для повышения производительности `Kafka` применяет микробатчинг: `batch.size` задаёт размер пакета, а `linger.ms` — время ожидания, чтобы накопить больше сообщений. Чем выше параметры, тем больше `throughput`, но возрастает задержка.

```java
props.put("batch.size", 32768); // 32KB
props.put("linger.ms", 5); // ждём 5мс для микробатча
```

---
**Consumer**

`Consumer` (потребитель) — это компонент `Kafka`, который читает сообщения из топиков.
Он используется в приложениях, которые должны обрабатывать или анализировать события, поступающие от продюсеров.

Например:

- микросервис заказов получает новые заказы,

- аналитика обрабатывает клики пользователей,

- система уведомлений реагирует на события в реальном времени.

🔹 **Оффсеты и коммиты**

Каждое сообщение в `Kafka` имеет уникальный порядковый номер — `offset` (смещение) внутри своей партиции.
Он показывает, на каком месте в очереди находится сообщение.

Есть два варианта. Автокоммит (`enable.auto.commit=true`) прост в настройке, но небезопасен: `consumer` может упасть между чтением и обработкой. Ручной коммит (`commitSync() или commitAsync()`) даёт контроль — фиксируем прогресс только после успешной обработки.

```java
consumer.commitSync(); // фиксируем оффсет после обработки
```


🔹 **Consumer group**

`Consumer group` — это группа консьюмеров, которые совместно читают данные из одного топика.
Все участники группы имеют одинаковый идентификатор — `group.id`.

💡 Как это работает

- Каждый топик в Kafka разбит на партиции (части потока данных).

- Когда несколько консьюмеров принадлежат одной группе (`group.id` одинаковый), `Kafka` распределяет партиции между ними.

- Каждая партиция читается только одним консьюмером в рамках одной группы, чтобы не было дублирования обработки.

Пример:

| Топик   | Партиции | Консьюмеры | Распределение                             | 
|---------|----------|------------|-------------------------------------------|
| orders  | 3        | 3          | каждый читает свою партицию               | 
| orders  | 3        | 2          | один читает 2 партиции, другой — 1        |
| orders  | 3        | 4          | 1 консьюмер останется без работы (лишний) |

⚙️ Настройка
```java
props.put("group.id", "order-service");  // все консьюмеры с этим group.id в одной группе
KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(Collections.singletonList("orders"));
```
🚀 Преимущества consumer group
1. Масштабирование

Добавляя больше консьюмеров в группу, ты можешь распараллелить обработку.
Каждый из них будет читать свою часть данных (свою партицию).

2. Отказоустойчивость

Если один консьюмер упадёт, Kafka автоматически перераспределит его партиции между оставшимися участниками группы.
Это называется rebalance.

3. Гибкость

Можно иметь несколько групп для одного топика.
→ Каждая группа будет читать все сообщения независимо (например, одна группа для аналитики, другая — для уведомлений).

**Модели доставки**

Модели доставки сообщений — это способы, которыми Kafka гарантирует доставку сообщений от продюсера к консьюмеру, определяя, как система ведёт себя при сбоях (повторной отправке, сбое сети, падении потребителя и т.д.).

| Модель          | Гарантия                                      | Риск                                            | Использование                                            | 
|-----------------|-----------------------------------------------|-------------------------------------------------|----------------------------------------------------------|
| `At-most-once`  | Сообщения доставляются не более одного раза   | Возможна потеря данных                          | Логирование, не критичные данные                         | 
| `At-least-once` | Сообщения доставляются как минимум один раз   | Возможны дубликаты                              | Уведомления, аналитика                                   |
| `Exactly-once`  | Каждое сообщение доставляется ровно один раз  | Требует идемпотентности и транзакций → сложнее  | Финансовые операции, биллинг, критичные бизнес-процессы  |


📌 Таким образом, модель доставки — это компромисс между скоростью, надёжностью и сложностью реализации.

### Упражнения

1. Создайте отдельный микросервис `Order Gateway`, который будет принимать новые заказы и публиковать их в `Kafka`.
2. В нем создайте класс `OrderGatewayService` с методами:
- `public static void main(String[] args)`;
- `public void sendOrder(String orderId, String orderData)`.
3. В методе `sendOrder`:
- настройте свойства `Properties` для подключения к `Kafka` (`bootstrap.servers`, `key.serializer`, `value.serializer`);
- создайте `KafkaProducer`;
- сформируйте `ProducerRecord` с топиком `orders.new`, ключом `orderId` и значением `orderData`;
- отправьте сообщение и выведите результат (успех или ошибка) в консоль.
4. В методе `main` создайте несколько примеров заказа (например `orderId = "order-1"`) и вызовите `sendOrder` с тестовыми данными.
5. Создайте второй микросервис `Order Processor`, который будет читать заказы из `Kafka` и обрабатывать их.
6. В нем создайте класс класс `OrderProcessorService` с методами:
- `public static void main(String[] args)`;
- `public void processOrders()`.
7. В методе `processOrders()`:
- настройте свойства `Properties` для `KafkaConsumer`;
- подпишитесь на топик `orders.new`;
- реализуйте бесконечный цикл чтения сообщений (`ConsumerRecords`) и поставьте консьюмеру паузу в 200 мс;
- добавьте простую валидацию заказа (например, проверку поля `email`);
- в зависимости от результата выведите сообщение в консоль:
  - если заказ корректен - успешная обработка и сообщение отправляется в топик `orders.processed`;
  - если заказ не прошел валидацию - ошибка и сообщение отправляется в топик `orders.failed`.
8. В методе `main` вызвать `processOrders()`.
9. В `Docker` должна быть запущена `Kafka`. Запустите сначала `OrderProcessorService`, потом `OrderGatewayService`.
Проверьте вывод в консоль.

**Дополнительные задания:**
1. Добавьте идемпотентность в продюсер и максимальную надёжность доставки сообщений.
2. Добавьте `group.id` для консьюмера.
3. Добавьте ручной коммит оффсета.
